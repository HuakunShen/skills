# The SVG screenshot pipeline

Every image in `assets/svg/` was generated by `examples/`, a real cargo project in this skill
folder — not drawn by hand, not a real terminal recording. Regenerate them after touching a scene
or the renderer:

```bash
cd examples
cargo run --bin render_gallery
```

This writes/overwrites every `assets/svg/*.svg` in one pass (a few seconds, no terminal/display
needed at all).

## Why buffer-to-SVG instead of recording a real terminal

The obvious approach — run the app in a real/virtual terminal (tmux, a pty, `asciinema`/`vhs`)
and convert the captured ANSI stream to an image — works, but adds a PTY, ANSI parsing, and
timing/animation-frame guessing to the pipeline. Ratatui already computes the exact ground truth
of what would be drawn — a `Buffer` of cells, each with a resolved `symbol`, `fg`, `bg`, and
`Modifier` — before any of that. `examples/src/bin/render_gallery.rs` draws each scene into a
`ratatui::backend::TestBackend` (an in-memory buffer, no real terminal at all), then
`examples/src/svg_export.rs::buffer_to_svg` walks that buffer directly into SVG markup: one
`<rect>` per run of same-background cells, one `<text>` per run of same-styled cells. No PTY, no
ANSI parsing, no flakiness, no "did I wait long enough for the frame to settle."

The other deliberate choice: text stays real `<text>` content, not a rasterized image. This means
an AI (or a human) can read the SVG's raw XML directly and see the actual on-screen text and
color values as text, without rendering anything — and it renders natively wherever Markdown
supports inline SVG (GitHub, most viewers).

## Terminal-window chrome

`buffer_to_svg` wraps the raw cell grid in a small rounded-corner "window": a dark title bar with
three macOS-style traffic-light dots and the scene's title, a drop shadow, Catppuccin-Mocha
colors for the default palette. Purely cosmetic — the cell grid itself starts right below the
title bar.

## Adding a new scene

1. Add a `fn my_scene(f: &mut Frame) { ... }` to `examples/src/scenes.rs`, using
   `crate::theme::THEME` for all colors (never a raw `Color::Rgb(...)` — see
   `reference/aesthetics.md` §1).
2. Add a `Scene { id, title, width, height, draw: my_scene }` entry to `scenes::all()`.
3. `cargo run --bin render_gallery` — it appears at `assets/svg/<id>.svg` automatically.
4. Reference it from the relevant `reference/*.md` with `![alt](../assets/svg/<id>.svg)`.

Pick `width`/`height` generously enough that the widget has room to look intentional — most
scenes here are 40-96 cols wide, 6-30 rows tall depending on content.

## Two real bugs this renderer had — read before modifying `svg_export.rs`

Both were caught by actually screenshotting the SVGs through headless Chromium and looking at
the result, not by reading the code — **if you touch `buffer_to_svg`, re-render and visually spot
-check at least `dashboard.svg` and `list_selection.svg` before trusting it.**

1. **A stray `x += 1` after a whitespace-only text run silently ate the first character of
   whatever run came next** (`"src/"` rendered as `"rc/"`, `"Cargo.toml"` as `"argo.toml"`). The
   inner loop that accumulates a same-styled run already leaves `x` pointing at the correct start
   of the next run when it breaks on a style change; the old code then advanced `x` *again* in
   the "this run was blank, skip it" branch, double-consuming one column. Fixed by not touching
   `x` outside the run-accumulation loop at all.

2. **Wide/exotic glyphs (Nerd Font private-use-area icons, some emoji) need
   `textLength`/`lengthAdjust="spacingAndGlyphs"` on every `<text>` run** — without it, a glyph
   the assumed monospace font doesn't actually cover falls back to a font with different advance
   width, silently drifting everything after it out of grid alignment (or, combined with the clip
   -path used for rounded corners, getting invisibly clipped off entirely — this is why an early
   version of `canvas_radar.svg` looked almost empty even though the underlying buffer was
   correct). `buffer_to_svg` now forces every run to occupy exactly `run_cols * CHAR_W`
   regardless of what font a given character actually renders with.

The practical corollary for *content*, not just the renderer: prefer plain single-width Unicode
symbols (`▪ ▸ ● ◆ ○ □ ★ ✓ ✗ ⚠`) over Nerd Font icons or emoji in anything meant to be screenshotted
this way — see the icon note in `reference/widgets-builtin.md`. Nerd Font glyphs only render
inside a terminal configured with a patched font (tofu boxes everywhere else); emoji are
double-width and this renderer's column math, like a lot of simple terminal-to-image tooling,
doesn't special-case that.

## Debugging a scene without images

`examples/src/scenes.rs` and `svg_export.rs` are plain library code — to check what a scene
actually draws before worrying about SVG rendering at all, dump the raw buffer as text:

```rust
// throwaway src/bin/debug_dump.rs
let scene = scenes::all().into_iter().find(|s| s.id == "canvas_radar").unwrap();
let mut terminal = Terminal::new(TestBackend::new(scene.width, scene.height)).unwrap();
terminal.draw(|f| (scene.draw)(f)).unwrap();
for y in 0..scene.height {
    let line: String = (0..scene.width)
        .map(|x| { let s = terminal.backend().buffer()[(x, y)].symbol(); if s.is_empty() { ' ' } else { s.chars().next().unwrap() } })
        .collect();
    println!("{line}");
}
```

This isolates "is the bug in my scene's widget usage" from "is the bug in the SVG renderer" —
exactly how bug #1 above was diagnosed.
