## 1. The "default stack" (dependency census)

Ranked by how many of the 22 apps declare each crate directly, with what it's actually used for:

1. **`clap`** (19/22) — CLI parsing/derive, shell completions, man-page generation.
2. **`serde`** (+ `serde_json`/`serde_yaml`, 17/22) — config files and app-state persistence.
3. **`crossterm`** (17/22 direct; the rest transitively via `ratatui::crossterm`) — raw mode,
   input events, alt-screen. The near-universal backend.
4. **`anyhow`** (16/22) — app-level `?` error propagation in the binary (vs `thiserror` inside
   library-ish modules, layered under it).
5. **`chrono`** (13/22) — timestamps in tables/logs.
6. **`unicode-width`** (11/22) — on-screen cell width of wide/zero-width characters before any
   column/truncation math. Skip this and CJK/emoji content breaks your layout.
7. **`tokio`** (10/22) — once you have concurrent I/O (network, subprocess, filesystem watch)
   alongside rendering.
8. **`thiserror`** (9/22), **`itertools`** (9/22), **`regex`** (9/22).
9. **`rand`**, **`strum`** (`EnumIter`/`Display` for cycling tabs/modes), **`tracing`**
   (structured logging to a file, since stdout is the UI) — 7/22 each.
10. **`indexmap`**, **`unicode-segmentation`**, **`ansi-to-tui`** — 5/22 each.
11. `tui-input` (3), `syntect` (3), `color-eyre`/`human-panic` (~4 combined),
    `ratatui-image`/`tui-textarea`/`tui-big-text`/`throbber-widgets-tui`/`tachyonfx` (1 each,
    see `reference/widgets-third-party.md`).

**Takeaway:** `ratatui` + `crossterm` + `clap` + `serde` + `anyhow`/`color-eyre` +
`unicode-width` is the realistic floor for a serious TUI; add `tokio` the moment rendering and
I/O need to overlap, and log to a file via `tracing` since your terminal is occupied.

## 2. Event-loop architecture — three shapes

### A. Synchronous poll loop (no channels, no async)

Simplest, right default for a small tool. Used by `csvlens`, `twozero48`, `trippy` (background
probing on its own threads, but the render loop itself is plain poll/read), `scope-tui`.

```rust
loop {
    terminal.draw(|f| ui::draw(f, &mut app))?;
    let timeout = if app.is_animating() { Duration::from_millis(16) } else { tick_rate };
    if event::poll(timeout)? {
        match event::read()? {
            Event::Key(key) if key.kind == KeyEventKind::Press => app.handle_key(key),
            Event::Resize(..) => app.mark_dirty(),
            _ => {}
        }
    } else {
        app.tick();
    }
    if app.should_quit { break; }
}
```

`chess-tui`/`twozero48` refine this with a fast poll while animating, blocking poll while idle —
power-efficient without sacrificing frame rate during a transition.

### B. mpsc-channel + dedicated input thread

A background thread blocks on `poll`/`read`, pushes a typed `Event` enum down an `mpsc::channel`;
the main thread just `terminal.draw()`s then blocks on `rx.recv()`. The "ratatui-template" idiom.
Used near-verbatim by `binsider`, `gpg-tui`, `minesweep-rs`, `chess-tui`. `bottom` and `gitui`
scale it to *multiple* producer threads (input, data-collection, cleanup-timer, fs-watch) fanned
into one consumer `match` (`gitui` via `crossbeam_channel::Select`). `bandwhich` is the outlier:
no central `Event` enum at all, just `Arc<Mutex/Atomic>` state shared between an input thread and
a fixed-cadence display thread that `park()`/`unpark()`s.

```rust
enum Event { Key(KeyEvent), Mouse(MouseEvent), Resize(u16, u16), Tick }
let (tx, rx) = mpsc::channel();
thread::spawn(move || {
    let mut last_tick = Instant::now();
    loop {
        let timeout = tick_rate.saturating_sub(last_tick.elapsed());
        if event::poll(timeout).unwrap() {
            match event::read().unwrap() {
                CrosstermEvent::Key(e) if e.kind == KeyEventKind::Press => tx.send(Event::Key(e)),
                CrosstermEvent::Resize(w, h) => tx.send(Event::Resize(w, h)),
                _ => Ok(()),
            }.unwrap();
        }
        if last_tick.elapsed() >= tick_rate { tx.send(Event::Tick).unwrap(); last_tick = Instant::now(); }
    }
});
while app.running {
    terminal.draw(|f| ui::draw(f, &app))?;
    match rx.recv()? { Event::Key(k) => app.handle_key(k), Event::Tick => app.tick(), _ => {} }
}
```

### C. tokio async, `Action`/`Event` through `tokio::select!` (Elm-style)

A `Tui` task races `crossterm::event::EventStream` against tick/render `interval`s inside
`tokio::select!`, sending typed `Event`s over an `mpsc::unbounded_channel`. The main loop turns
`Event`s into `Action`s via a keymap, then dispatches every `Action` through one big `match`
reducer. Essentially the community "ratatui async template" — appears near-identically in
`openapi-tui`, `rainfrog`, `television`, `taskwarrior-tui`. `oatmeal`/`oxker` use a lighter two
-channel variant. `xplr` and `slumber` implement the purest Elm shape without the interval-select
idiom: xplr's reducer is `fn handle_task(self, task) -> Self` returning a new `App` plus a
`VecDeque<MsgOut>` side-effect queue; slumber runs a `!Send` `Rc<RefCell<...>>` queue on a
`tokio::task::LocalSet`.

```rust
enum Event { Key(KeyEvent), Tick, Render, Resize(u16, u16) }
enum Action { Tick, Render, Quit, MoveDown, Submit, /* …domain actions… */ }

tokio::spawn(async move {
    let mut reader = crossterm::event::EventStream::new();
    let mut tick = tokio::time::interval(tick_delay);
    let mut render = tokio::time::interval(render_delay);
    loop {
        tokio::select! {
            Some(Ok(evt)) = reader.next() => event_tx.send(Event::from(evt)).unwrap(),
            _ = tick.tick() => event_tx.send(Event::Tick).unwrap(),
            _ = render.tick() => event_tx.send(Event::Render).unwrap(),
        }
    }
});
loop {
    if let Some(event) = event_rx.recv().await {
        if let Some(action) = keymap.action_for(&event) { action_tx.send(action)?; }
    }
    while let Ok(action) = action_rx.try_recv() {
        match action {
            Action::Tick => app.tick(),
            Action::Render => tui.draw(|f| ui::draw(f, &app))?,
            Action::Quit => return Ok(()),
            other => app.update(other)?,
        }
    }
}
```

**Pick based on need, not novelty:** start with A; move to B the moment input handling needs to
not block rendering; move to C only once you have real concurrent I/O to coordinate.

## 3. Notable custom widgets (when built-ins aren't enough)

- **`bottom`'s `PipeGauge`** (`src/canvas/components/pipe_gauge.rs`) — `impl Widget`, fills `|`
  characters cell-by-cell up to a ratio with multiple label-hiding strategies chosen by available
  width. `bottom` also vendors and hand-modifies ratatui's own `Chart`/`Canvas` for finer braille
  control than the stock widgets expose.
- **`csvlens`'s `CsvTable`** (`src/ui.rs:914-996`) — `impl StatefulWidget`, operates directly on
  `Buffer`: row-number gutters, frozen columns, wrapped rows, hand-drawn T-junction border
  intersections — spreadsheet behavior no stock `Table` supports.
- **`gitui`'s `Scrollbar`**/**`StatefulParagraph`** (`src/ui/scrollbar.rs`,
  `src/ui/stateful_paragraph.rs`) — hand-drawn track/thumb; a `Paragraph` reimplementation with
  independent horizontal *and* vertical scroll for diff/blame views.
- **`joshuto`'s ~20 `impl Widget` types** (`src/ui/views/*.rs`) — the entire UI hand-built,
  including hand-drawn T-junction borders where three ranger-style panes meet.
- **`taskwarrior-tui`'s `Table`** (`src/table.rs`) — column widths solved via ratatui's own
  cassowary constraint solver; a hand-drawn multi-month `Calendar` (`src/calendar.rs`).
- **`rainfrog`'s `ScrollTable`** (`src/components/scroll_table.rs:324-379`) — renders into an
  off-screen `Buffer` sized to unclamped content, blits a windowed x/y-scrolled slice into the
  visible area for arbitrarily large 2-D-scrollable grids (modeled on `tui-textarea`'s approach).
- **`oatmeal`'s `BubbleList`** (`src/domain/services/bubble_list.rs`) — writes cached pre-wrapped
  `Line`s directly via `buf.set_line(...)`, caching per-message wrap/highlight so a chat bubble
  isn't re-wrapped every frame.
- **`binsider`'s `Logo`** (`src/tui/widgets/logo.rs`) — parses an embedded true-color ANSI-art
  string via `ansi_to_tui::IntoText`, overlays a caption computed from the logo's fixed size.

When nothing off-the-shelf fits, implementing `Widget`/`StatefulWidget` and writing straight into
buffer cells (`buf[(x, y)].set_symbol(...).set_style(...)`) is completely normal here — these are
real, shipped examples, not exotic escape hatches.
