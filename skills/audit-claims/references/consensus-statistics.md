## 1. 先配置实际要用的模型

在每次运行的 `config/` 中保存两份互相一致的文件：

- `model-selection.md`：用户可读的选择记录，包括问题、回答、适用范围、预算说明和选择日期。
- `model-policy.json`：机器可读的模型清单、角色与验收策略。封存后的策略指纹和锁文件由 `scripts/model_panel.py` 管理。

使用 `config/model-policy.lock.json` 及其 `policy_hash` 固定当前策略。人工编辑配置后必须重新校验与封存，产生明确的新一轮；不能把旧模型结果当作新策略已满足。复用已明确授权且仍适用的配置，不要每次都要求用户重复回答。

启动时只询问尚未确定且会改变执行的选择：

1. **选哪些模型？** 显示当前环境实际可用的候选与能力/费用信息，让用户指定有限清单。不要把「支持多模型」解释为调用所有可用模型。
2. **谁做什么？** 区分检索、批量提取、事实核验、报告评分与 judge。用户可以给同一模型多个角色，也可保留单 agent。
3. **事实如何验收？** 在 `single`、`unanimous`、`judge`、`human` 中选一个；确认指定核验员与 judge。
4. **报告是否多模型？** 指定报告评分模型、是否需要最终 judge，以及共同评分标准。未选报告 panel 就只按单模型流程写报告。
5. **预算与异常怎么办？** 记录预计增加的调用量、成本、并发、失败和分歧处理。模型可用和计价已知不代表费用已获授权。

已有用户指示能回答这些问题时，直接填入，不再制造审批步骤。配置仍是 draft 时，可以继续清单整理和免费确定性处理，但不得自行选一组付费模型开始调用。

机器策略使用以下字段；具体校验以随包脚本为准：

| 字段 | 含义 |
| --- | --- |
| `selected_models` | 明确选中的 `{id, provider, api_model, availability, cost}`；不填密钥 |
| `roles` | `lookup`、`extract`、`verify`、`report`、`judge` 对应 model ID 数组 |
| `verification.mode` | `single | unanimous | judge | human | tiered` |
| `verification.required_reviewers` | 本轮必须提交有效记录的指定核验员 |
| `verification.judge_model_id` | judge 策略使用的指定模型；不需要时 null |
| `verification.escalation` | `hold`（默认）或用户预先选定的 `human`；仅对符合条件的未决分歧升级 |
| `report.reviewers` | 报告/评分的指定模型；单模型也填一个 ID，多模型填所选清单 |
| `report.judge_model_id` | 报告最终 judge；可为 null |
| `max_models` | 清单上限，默认 5 是容量限制，不是必须调用 5 个 |
| `allow_unlisted_models` | 默认 false；不可自行扩大清单或换成更贵模型 |
| `status` | `draft | confirmed`；confirmed 表示选择已由用户指示确定 |

`availability` 为 `available | unverified | unavailable`。费用记录中 `mode` 为 `metered | included | local | unknown`，保留 `estimate_usd`，并建议记录 `pricing_checked_at`；不知道的填 null，不能当成免费。只有实际访问过的能力才能标为可用。

模型 ID 需定位实际 provider、API model 与可得版本；「Sonnet」「Flash」之类家族标签不足以证明实际模型身份。不同别名调用同一个底层模型时明确标出，不能因此宣称多模型独立验证。

## 2. 把事实提案与最终裁决分开

核验员输出的是**提案**。在验收策略通过前，提案必须保存在 `reviews/`，不能直接覆盖 `claims.jsonl` 的最终裁决。协调者保存全部结果、遗漏、弃权、冲突、重跑与决定，再将通过策略验收的结果合并到 canonical 账本。

每条 fact vote 包含：

```json
{
  "vote_id": "unique-review-record-id",
  "reviewer_id": "a-selected-model-id",
  "claim_id": "the-canonical-claim-id",
  "criteria_hash": "frozen-criteria-hash",
  "input_hash": "frozen-task-input-hash",
  "as_of": "the-exact-run-cutoff",
  "verdict": "supported",
  "normalized_result": {},
  "evidence_ids": [],
  "rationale": "Evidence-based explanation; fill actual values before execution.",
  "independent": true
}
```

此示例只展示字段，不是一张有效的支持票：确定性裁决必须有可读取的证据。`normalized_result` 按任务的固定结果契约填写，例如目标数值及单位、事件是否发生、适用日期或规则逐项匹配结果；它不是自由发挥的摘要。

同一轮所有核验员必须核验相同 `claim_id`、原文、`criteria_hash`、`input_hash`、`as_of`。各自找到的证据可以不同，所以证据包哈希与证据 ID 单独记录，不并入要求相同的事实任务 input hash。每条证据的发生/发布/读取时间仍需满足截点政策。

确定性票只允许 `supported | contradicted | mixed`，需要非空 evidence_ids 和非空 normalized_result。协调者按 canonical JSON 精确比较 `{verdict, normalized_result}`；因此在派发任务时就要固定规范化字段、顺序无关的对象编码、数值精度和单位，不把长篇理由塞入这个比较对象。

完全相同的标签不一定代表同一结论：「支持」但一个认为是 10 个、另一个认为是 100 个，不能算共识。先用冻结的单位、时区、字段和容差规范化 `normalized_result`，再比较；不能取证后放宽容差来制造一致。源 ID 不同不算冲突，数值/事件语义不一致才需要检查。

`abstain` 表示该核验员无法形成裁决，与 `indeterminate` 不同：后者是对本次证据无法确定结果的判断。缺失、工具错误、空文件、格式无效和旧输入结果既不是赞同，也不是有效弃权。

## 3. 四种事实验收策略

| 策略 | 通过条件 | 遇到分歧时 |
| --- | --- | --- |
| `single` | 指定的一个核验员提交有效、证据合格的结果 | 按普通复核流程处理；不宣称多模型共识 |
| `unanimous` | 每个指定核验员都提交有效结果；所有规范化裁决相同；无弃权 | 保留冲突并暂停此条的最终验收，继续其他任务 |
| `tiered` | 低风险条目先由初轮模型核验（配合随机抽检）；高风险、反驳或分歧条目升级至 `escalation_reviewers` / `judge` | 自动升级复核，不降低高风险项验收门槛 |
| `judge` | 指定核验员的记录齐备，指定 judge 读取证据并出具具名决定（默认不得等于唯一 reviewer） | judge 可接受、修订或保留争议，必须说明证据理由 |
| `human` | 指定核验员（可为空）的记录齐备，用户对证据与分歧作出明确决定 | 记录人类决定；未回答之前继续保持未验收 |

若已采纳裁决事后遇到数据修订、新证据或归属更正，使用 `adopt_verdict.py reopen --run <RUN> --claim-id <ID> --reason <REASON> --actor <ACTOR>` 保留不可变历史并显式重开，禁止直接手工修改已采纳的 `claims.jsonl`。

所有策略都检查指定核验员是否齐备。正常弃权是有效提交，但它不会帮助满足 unanimity；judge/human 可以在明确看到弃权与原因后作出决定。某个指定模型缺席时不得把剩余票伪装成全体一致，或自动切换到多数/仲裁模式。

本版本不以 quorum、多数票或加权投票代替 unanimity。用户日后若明确要求这些规则，先扩展策略与校验并冻结新版本；不能仅在解释中声称已经支持。`unanimous` 中出现冲突时，主 agent **没有默认仲裁权**。默认保持未决；若预先配置 `verification.escalation=human`，则可按已授权升级规则交给用户，无须临时更改策略。

human 升级只适用于所有指定核验记录齐备后的真实分歧/弃权，或 judge 已明确给出 indeterminate。缺席记录不能用人类升级绕过，明确一致的结果也不能借此通道改写。judge 升级记录必须嵌入完整 `prior_judge_decision`，重验其模型身份和 considered_vote_ids；保留基础 mode、`resolution_route=human_escalation` 和 escalation_reason。人类无法确定时继续未验收。

`indeterminate` 与 `abstain` 都不自动通过验收，即使所有模型都给出同一标签也不通过。可以一致登记「仍无法确定」作为过程记录；它不能进入 supported/contradicted 计分。judge/human 若有足够证据形成确定性决定，须记录显式决定；否则继续未验收。

对于概率预测，共识对象是冻结事件是否发生及证据。投票包装层可用 `verdict=supported` 表示事件观察有充分证据，并在 `normalized_result.event_occurred` 写 true 或 false；这不是给原来的概率预测判正确。合并到 canonical 预测时，保留 `evaluation_mode=probabilistic`、`outcome=null`，仅写入已确认的 event_occurred 和证据，由 Brier 公式处理。

judge 或 human 的决定单独保存，至少包括：`decision_id`、`actor_type`、`actor_id`、相同任务指纹、结论、规范化结果、证据、理由和全部 `considered_vote_ids`。`actor_type` 为 `model | human`；模型 judge 必须匹配已配置身份。人类决定另带 `user_approval_reference` 指向用户实际选择的记录；身份记录是系统所记录的声明，不应夸称具备密码学签名认证。judge/human 策略即使首轮意见一致也要求显式决定；single/unanimous 仅可使用本策略预先允许且满足条件的升级，不能靠额外 decision 文件绕过。

judge 不得仅写「2 比 1，所以成立」。它应指出哪个事实、定义、单位或证据解释导致差异，引用解决差异的资料；可以认为少数票更可靠，也可以拒绝形成结论。judge 发现冻结规则有缺陷时，返回规则修订请求，保留旧规则与旧票，重新冻结并重跑；不能单独修改规则后宣布旧票已达成一致。

向人类提交问题时，提供紧凑的差异表：原话、判定规则、每个模型结论及依据、真正冲突点、缺失事实、可选处理。避免把整段模型输出直接当成需要用户自行整理的审阅材料。用户尚未决定时，将其他无争议条目继续完成。

## 4. 多模型独立报告与 judge

多模型报告与事实验收是两层任务，可以只启用其中一层。某人所有事实都已一致验收，并不要求所有模型的定性评价一致；报告间一致也不能反过来豁免事实核验。

报告 panel 的每个模型收到同一个已冻结的语料/claim/evidence 快照、统一 rubric、量表、范围、截点和确定性统计。首轮不展示其他模型的结论、分数或模型名称，减少相互模仿；记录 `independent=true` 表示**独立执行且未见同伴输出**，不表示统计独立。

分清两类数字：

- `strict_support_rate`、accountability、成本、样本量等确定性统计，来自同一账本和脚本，应完全一致。模型不能凭印象重新估计；出现差异先修复输入或计算问题。
- 明确定义的定性 rubric 分数，例如论证透明度、承认不确定性、更新一致性，由各模型独立给分并引用案例。这类分数可做描述性比较。没有证据或不适用时填 null，不能填 0。

每个报告保存 `review_id`、`model_id`、`data_hash`、`rubric_hash`、`score_scale`、`scores`、`status`、`independent`，并关联原始报告文件、调用轮次及实际模型版本。不同数据、量表、rubric 或截点的分数不得放入同一组统计。

统计前每个计划模型只接受一份 terminal review；重复提交必须明确 superseded 或单列重复实验，不随意选更好看的结果。同模型多次采样是重复运行，不是新增独立模型。不同温度、提示或 seed 作为单独的实验因素报告，不能混充模型数量。

完成首轮后再由指定 judge 阅读报告，可以使用匿名标签 A/B/C。judge 输出独立的最终报告/分数、理由、与各报告的分歧及证据。不要求最终分数等于平均值；如果偏离平均值或范围，应说明原因。它不能悄悄改写 raw scores，也不能改 canonical 事实；新发现的事实问题退回核验流程。

最终展示顺序：各模型原始分数与理由 → 模型间描述统计 → judge 的最终判断与原因。用户要人类作最后选择时，保留同样资料，由人类决定后追加记录。

## 5. 描述模型间分歧

对同一指标的有效分数 `x₁,…,xₙ`，默认等权，仅计算：

- `n` 与 `planned_n`：实际有效模型数与计划模型数，另列缺失/弃权/无效记录。
- `mean = sum(x)/n`。
- `sample_variance = sum((x-mean)^2)/(n-1)`，仅 n≥2。
- `sd = sqrt(sample_variance)`，仅 n≥2。
- `median`、`min`、`max`、`range = max-min`。

n=0 时数值统计均为 null；n=1 时均值/中位数/最小/最大是该分数、range=0，方差和标准差为 null。n=2–5 只能描述这组所选模型；不要自动输出正态置信区间、显著性检验或「真实可信度」概率。计算 `n−1` 的方差公式本身不意味着模型是随机独立抽样。

例如合成分数 `[72,78,90]` 的 mean=80、sample variance=84、SD≈9.17、median=78、range=18。可以写「三个选定模型的平均评分 80，模型间标准差 9.17」，不能写「真实可信度为 80±9.17，95% 可信」。

每个维度分别统计，分母可能不同；报告有效模型清单。模型弃权或不适用不以 0 填补。支持/反驳标签不能编码为任意数字后求平均来生成事实结论。未经用户设定，不按模型价格、品牌或自报 confidence 加权。

可视化优先展示每个模型的点以及明确标注的 min–max 或 ±SD。图例必须说明误差线定义；无法确认一张既有截图的误差线含义时，标「未定义」，不要猜成标准差、置信区间或后验区间。

## 6. 不把模型分歧当成统计置信区间

中央极限定理讨论在适当抽样和矩条件下**样本均值的抽样分布**随样本量增大趋近正态；它不保证原始分数本身正态，也不使任意三五个模型评分自动成为可作总体推断的随机样本。[NIST 的定义](https://csrc.nist.gov/glossary/term/central_limit_theorem)

这里的模型通常是人为挑选，且可能共享训练来源、模型家族、搜索工具、证据和 rubric。因此默认不把模型当独立同分布观察，不把 `sd/sqrt(n)` 解释为真实性的标准误，也不把更多重复调用当作增加独立证据。

「所有模型都给高分」只表示本组模型在给定输入与口径下接近；共享错误证据会产生一致错误。「方差很大」表示需要检查分歧，原因可能是输入缺失、rubric 不清、归属错误或判断不同，不能直接推出对象本人不可靠。

频率学派的 95% 置信区间描述的是在设定抽样机制下重复构造区间的长期覆盖性质，不等于把某个固定参数说成有 95% 概率落在已计算区间。[NIST 的解释](https://www.itl.nist.gov/div898/handbook/prc/section1/prc14.htm) 本 skill 默认的模型间 range/SD 没有这个覆盖承诺。

报告明确区分：**模型间分歧**、**语料/事件抽样不确定性**、**事实证据不足**与**方法选择敏感性**。四者分别报告，不能合成一个未经定义的 error bar。

## 7. 可选的语料内不确定性分析

这与模型 panel 的 n 个分数是不同任务。只有用户需要推断超出已观察样本的表现，且有足够可比、相对独立的事件家族时，才考虑 bootstrap。若已完整审计选定时间范围的全部可取得内容，先说明汇总分数是该有限语料的描述；重抽样区间不消除缺失内容或错误裁决。

bootstrap 用观测样本的重抽样近似估计量的抽样分布，其解释依赖所模拟的抽样机制。[Efron (1979)](https://doi.org/10.1214/aos/1176344552) 对相关/成组资料，如何选择数据模型与重抽样单位会影响方差估计，不能机械逐句独立重抽。[Field & Welsh (2007)](https://researchportalplus.anu.edu.au/en/publications/bootstrapping-clustered-data/)

可采用以下**额外分析规范**，不默认声称随包脚本已经实现：

1. 先声明估计目标：例如固定领域和预测期限组合下，类似未来事件的平均支持率。声明把哪些观察视为样本、目标总体是什么。
2. 把同事件的重复、预测更新和强相关命题归入 event/claim family；以整个家族为重抽样单位，保留其内部关系与权重。
3. 如设计需要保持领域/年份构成，在事先定义的 strata 内对家族有放回抽样。家族跨多个层时按预先确定的单一分层规则分配，或使用更合适的多层设计；不要拆开相关组来凑样本量。
4. 每次重抽样重新计算完整指标和分母，保存随机 seed、重复次数、有效重复数、空分母次数与区间算法。至少使用足以稳定所报分位数的重复次数；多跑重复不弥补独立家族数量不足。
5. 比较两个评估方法或模型在**相同事件组**上的得分时，使用相同重抽样索引计算每轮分数差，报告差值分布。比较两个创作者只有在事件组确实可配对时才这样做；无可比事件不能假装 paired。
6. 独立家族太少、分层单元稀疏、事件存在明显时间相关或边界/退化分布时，不产出具有强覆盖含义的区间；可先报告 leave-one-family-out 敏感性、扩大样本或选择适合依赖结构的方法。

不允许把 3 个模型分数重抽样几千次，然后声称得到个人真实性的 95% 总体区间。只对现有错误标签反复抽样也不能估计事实核验错误；需另用独立复核或有人工真值的验证集来研究这类误差。

如果执行这种扩展，把结果保存在独立的 uncertainty 文件，明确标签、假设与方法版本；模型间描述统计仍保持单独输出。

## 8. 阻塞、重跑与审计记录

始终保留策略版本、每轮指定模型、任务输入指纹、每张票、原始模型输出、证据、费用、分歧摘要和最终决定。推荐为每次调用使用独立 review ID；追加 supersedes 关系，而不是覆盖旧文件。

新增证据或修订规则后，创建新的输入快照/轮次并使相关旧验收失效，保留其历史。新增模型需要用户选择并更新策略，不能为了打破平票无限召集模型直到满意。

仅在验收通过时由协调者写入 canonical `acceptance={decision_path,decision_sha256,policy_hash}`，关联决定路径、文件哈希、策略哈希、任务指纹与使用的 reviews。`model_panel.py consensus` 只生成机械验收结果，不自行修改 claims 或 evidence。未通过的条目留在 `reviews/` 和待复核队列；恢复运行时先读取锁定策略和这些记录，不重复调用已完成且仍匹配的模型。

通过 `adopt_verdict.py adopt` 保存正式裁定；`score_claims.py` CLI 在同一个 coordinator 锁内重新验证各个已接受裁定的原始票、规则、来源、证据与历史哈希。仅手动设置 review_state=accepted 不足以通过。`--run` 默认是 claims 文件所在目录；从导出快照评分时必须提供完整可追溯运行目录。纯 Python `calculate()` 只负责确定性指标计算，不能替代 CLI 的正式报告验收。

脚本负责配置校验、共识条件与描述统计；它不证明外部模型真的独立运行，也不证明 evidence IDs 对应的来源内容正确。协调 agent 仍须核对原始调用记录、文件存在与引用内容，诚实报告无法认证的部分。
